How a change becomes a page

The public route is rebuilt from the source that owns its content

The Harness first identifies the site’s content model, then changes the canonical source and lets the build reproduce the page.

Route + requirementPublic URL · audience · owner · source · acceptance criteria
→
Canonical sourceStructured page, use case, reusable fact, or maintained legacy HTML
→
Static-site buildRender pages, inject shared navigation and analytics, preserve integrations
→
dist/ artifactGenerated files mirror the public route structure used by Cascade
Examples of source ownership: generated pages live in content/pages/; maintained snapshot pages remain under src/site/.
Why it matters: the agent changes the durable source, while generated output stays reproducible and out of the review diff.

Risks and controls

People manage the risks that automation cannot decide

Clear sources, bounded context, human judgment, and live verification protect the audience and the institution.

Risk
Control
Inaccurate or stale contentA draft may use the wrong source, miss context, or make an unsupported claim.
→
Source and owner reviewUse approved sources, named owners, review dates, and direct claim checking.
More context than the update needsConnected files or tools may expose information outside the intended scope.
→
Bounded permissionsGrant only the connections needed and keep restricted or sensitive content out of public work.
Accessibility or brand gapsAutomated checks cannot make every content, keyboard, zoom, or screen-reader judgment.
→
Automated and human reviewCombine validation with responsive, keyboard, zoom/reflow, and assistive-technology spot checks.
Unexpected site or release impactA focused update can affect routes, integrations, or differ from the approved preview after publishing.
→
Focused scope and live verificationPreserve existing services, validate the site, and compare the live page with the approved result.
The Harness is an early pilot and changes quickly. Confirm the current supported capabilities and service path before relying on a workflow.

The production publishing path

A merge to main starts a three-stage Cascade release

Approve + mergeFocused pull request records the source diff, evidence, and human release decision
→
Build + planSITE_BASE_PATH='' · build · validate · dry-run Cascade upload
→
Upload exact artifactThe reviewed dist/ bytes are uploaded to the TritonAI site in Cascade
→
Queue publishCascade receives the folder publish request; queued does not mean finished
→
Verify productionOpen the public URL and compare content, controls, links, and behavior with approval

GitHub is the source-control and review record. Cascade is the production publishing system. The public page is the final source of release truth.
