Context

Why we moved off Cascade

Before — Cascade Server

  • Edits made inside a CMS web interface
  • Publish runs through a server queue
  • Version history lives in Cascade
  • Preview requires a staging server
  • One person can edit a page at a time

Now — GitHub + TritonAI Harness

  • Edits made in Markdown and JSON files
  • A build script generates the finished HTML
  • Git tracks every change with a full history
  • Automated checks run before anything goes live
  • Multiple contributors work at the same time
The public URLs, UC San Diego Decorator look and feel, and browser integrations are all preserved. What changed is how content gets in.
01

Where content lives

Understand the file structure and you understand the site.

The repository

Content is organized by type

Pages

content/pages/

Homepage, strategy, trust architecture, tools — the pages people read often. Markdown files with frontmatter.

Newsletters

content/newsletters/

One Markdown file per week. The homepage and AI Updates page pick them up automatically.

Use cases

content/use-cases/

Real campus AI workflows. Each carries a status, owner, and review date.

Media

content/media/

Article archive as JSON. Both media pages are generated from this file.

Structured data

content/roadmap/, facts/, skills/

Roadmap milestones, public claims, and the skills catalog — all JSON with required fields.

Visual shell

src/site/

The UC San Diego Decorator header, footer, styles, and scripts. Loads from the UCSD CDN. Rarely edited.

If a file lives under content/, you edit the source and the build writes the page. If it lives under src/site/, it is a legacy page edited directly at its original path.

What happens at each step

  • Build — scripts/build.mjs reads every content file, applies the Decorator shell, injects the Google Analytics tag, and writes finished HTML to dist/.
  • Validate — scripts/validate.mjs checks routes, links, metadata, analytics, freshness, and Decorator conformance.
  • Test — An axe-based accessibility scan runs at mobile and desktop widths. A language check flags booster words and heading problems.
  • Review — A pull request shows exactly what changed. Checks must pass before merge.
  • Publish — Merging to main triggers GitHub Actions to build and deploy to GitHub Pages automatically.
03

How multiple contributors work together

Branches, ownership tiers, and section markers keep concurrent work safe.

Contribution mechanics

Everyone works on a branch

No one edits main directly. Every contributor — human or agent — creates a feature branch named for the work:

content/update-strategy-2026-07-30     # a page edit
content/newsletter-2026-07-27          # a weekly update
automation/sync-ai-news                # an automated job

Two people can edit different parts of the site at the same time. Each branch becomes a pull request. main only receives changes through a merge.

Avoiding conflicts

  • Check open PRs before starting — if someone is already editing the same file, coordinate first
  • Keep PRs focused — one page or one task per PR
  • Pull main before merging and re-run npm test against the latest state
  • Stage only the files your PR is about — leave stray edits alone

Who can edit what

Edit ownership tiers

Agent-owned

Edit freely

Newsletters, media archive, release notes, and metrics sections. Agents may open PRs without a content owner's sign-off.

Human-owned

PR only, never direct commit

Strategic narrative, roadmap, and sustainability policy. The content owner reviews before merge.

Shared

PR with content-owner review

Homepage, TritonGPT landing, tools listing, and developer page. Both agents and people can edit, but the owner reviews.

Conflict prevention

Section markers protect generated regions

Generated or agent-managed regions inside a file are wrapped in HTML comment markers:

<!-- AGENT_SECTION: media-articles -->
...generated content...
<!-- END_AGENT_SECTION -->

Inside the markers

The build or sync job owns this region. It replaces only what is inside the markers on every run.

Outside the markers

A human can safely edit anything outside the markers in the same file without the build clobbering their work.

This lets a person and an automation edit the same file at the same time — each in their own region.

When automation and people overlap

Automated jobs and people can work in parallel

  • The job's PR and the person's PR are on separate branches
  • The job never force-pushes to a person's branch — only to its own automation/sync-* branch
  • If both PRs touch the same file, GitHub flags a merge conflict when the second one is merged
  • Rebase the second branch onto main, resolve the conflict, and re-run npm test
  • Because the job is idempotent, re-running it after a merge produces a clean result with no duplicates

Automated content jobs

Three scheduled jobs find and add content — a human still reviews before publish.

Scheduled automation

Three jobs that run on their own

Mondays 18:15 UTC

Newsletter sync

Pulls new editions from the external newsletter source into content/newsletters/. Opens a PR on automation/sync-ai-news.

Mondays 18:30 UTC

Media coverage search

Searches DuckDuckGo for TritonAI and TritonGPT articles, adds them to content/media/articles.json, regenerates both media pages. Opens a PR.

Hourly at :17

Skills Library refresh

Updates content/skills/library.json from the upstream GitHub repository. Builds in place — no PR needed.

None of these jobs publish directly. They open or refresh a PR, and a person merges it. Each job runs the full npm test suite before opening the PR.
05

Checks that must pass

Every change runs through five layers of automated review before it can merge.

The npm test suite

Five layers of automated review

  • Unit tests — UX-agent helpers, newsletter sync, and media coverage sync run first, before the build.
  • Build — Reads all content, applies the Decorator shell, injects analytics, writes HTML + sitemap + routes.
  • Validation — Content schema, broken links, remote dependencies, freshness, metadata, analytics, navigation, Decorator conformance, performance, routes, sitemap.
  • Accessibility scan — axe-core at 390 px and 1440 px, horizontal overflow, keyboard behavior, button sizing.
  • Language check — Booster words, manufactured contrast, heading sentence breaks, long lists, em dashes, repeated opening frames.
Automated checks do not replace manual review. After changing a page, look at it at desktop and responsive widths and confirm headings, links, and keyboard focus behave.

Validation in detail

What the validator checks

Content and structure

  • Content schema — required fields on every page, use case, fact, milestone, and skill
  • Broken links — every internal link must resolve
  • Remote dependencies — Decorator, search, widget, and feed must respond over HTTPS
  • Freshness — warns after 120 days, fails after 365
  • Retired content — no links to retired routes or internal filenames

Presentation and performance

  • Metadata — canonical URL, Open Graph, Twitter card, JSON-LD
  • Analytics — exactly one tag, correct ID, asynchronous
  • Navigation — ARIA relationships, active state, duplicate IDs
  • Decorator — stylesheets, extension class, no inline fonts
  • Performance — deferred video, lazy YouTube, preconnect, image budget

Accessibility is a gate, not a suggestion

The accessibility scan

Every non-redirect route opens in headless Chromium at two widths — 390 px and 1440 px — and runs axe-core plus interaction checks:

axe-core

WCAG automated checks

Color contrast, landmarks, headings, labels, names, and ARIA correctness.

Interaction

Keyboard behavior

Navigation dropdowns, toggles, and search controls must respond to keyboard focus and activation.

Layout

Overflow and sizing

No horizontal scroll at either width. Collapsed hub media and mismatched button sizes are flagged.

Results are written to reports/accessibility.json and uploaded as a GitHub Actions artifact that stays for 30 days.

Voice and language

The language check reads the source, not the HTML

It reads Markdown in content/ so a finding names the file an editor would open. It flags:

  • Heading sentence breaks — a heading with two sentences reads as a slogan
  • Count in a heading — when the list below already shows the count
  • Manufactured contrast — "X, not Y", "rather than", "instead of"
  • Booster adjectives — "practical", "seamless", "leverage" — words that do no work
  • Long comma lists — five or more items should become a list element
  • Em dashes — outside numeric ranges, use a period or comma
  • Repeated opening frames — when sibling strings all start the same way
  • Description length — frontmatter descriptions under 155 characters
Governance vocabulary — "approved", "bounded", "supervised", "named owner" — is never flagged. Those qualify real controls.

What to take home

Summary

Key takeaways for Cascade content staff

  • Content lives in files, not in a CMS. Markdown and JSON under content/ are the source. The build writes the HTML.
  • Every change goes through a pull request. A branch, a review, a merge. No direct edits to main.
  • Multiple contributors can work at once. Branches, ownership tiers, and section markers prevent conflicts.
  • Three jobs find content automatically. Newsletters, media coverage, and the skills catalog — each opens a PR for review.
  • Five check layers run before merge. Unit tests, build, validation, accessibility, and language. If any fails, the PR cannot merge.
  • Merge to main publishes. GitHub Actions builds and deploys to GitHub Pages. No manual upload.
